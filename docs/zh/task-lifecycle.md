## 工作树与任务结束

`managed` 仍为默认策略，新增可选 `baseBranch`，仅接受已有本地分支。缺省在首次准备时读取源目录当前分支，冻结其提交；工作树继续放在扩展工作区存储目录中。源目录可以有未提交修改，这些修改不复制到隔离目录。`current`／`branch` 直接模式保留原有干净目录要求与分支切换语义。

Reviewer 验收通过只结束执行。宿主另存对应文件内容的验收标识，任务目录与分支保持。显式提交前展示文件清单和提交说明，重新核对预览令牌；提交包含当前非忽略 Git 修改。提交后内容一致的验收仍可用于检查任务分支，但不代表合入目标后的项目已经验证。

合入仅接受已提交且与已通过验收内容一致的任务，使用普通合并，允许快进，不 squash、rebase 或推送。目标为源目录当前分支时要求源目录干净；未检出的其他本地目标使用扩展管理的临时工作树。外部工作树占用目标时返回位置并阻止操作。合并前记录来源／目标提交、目录与操作 ID；冲突保留现场，提供宿主检查、完成和中止接口。完成要求冲突已人工解决并暂存。任何合入结果都标记为仍需验证，不沿用源任务的验收结论。

操作按公共 Git 仓库在宿主内串行，并使用 Git 引用更新、状态令牌和持久化操作记录防止重复提交或错误重试。这不是与任意外部 Git 客户端的跨进程原子事务；检测到分支、文件或合并状态变化时阻止后续操作。Git 调用继续禁用钩子、内容过滤器、外部差异和自定义合并驱动，避免仓库配置触发外部程序。

## 安全清理与恢复

显式清理只适用于登记属于 DualMind 的隔离工作树。执行和子进程停止确认后，先持久化清理意图与文件清单，再以 `git stash --all` 保存未提交内容，并建立固定 `refs/dualmind/snapshots/<id>/head` 和 `/work` 引用。实际文件内容与 Git 对象逐项核对成功后才移除工作树。普通 `stash@{n}` 序号只会变动，不能作为恢复身份。

保存包括暂存、未暂存、未跟踪及非可再生成的忽略文件。排除项仅为完全未跟踪的 `node_modules`、`.venv`、`venv`、`target`、`dist`、`build`、`coverage`、`.next`、`.cache`、`__pycache__` 目录，并在预览中列出；含已跟踪文件的同名目录不排除。扫描仍检查排除目录中是否存在嵌套 Git 仓库。Git 保存文件内容、符号链接及暂存状态，清单另记普通文件权限；不承诺保存 ACL、扩展属性或时间戳。

上限为待保存文件总量 256 MiB、20,000 个文件、扫描 200,000 个目录项；Git 命令仍受 20 秒和 2 MiB 输出保护。特殊文件、硬链接、嵌套仓库、子模块、目录重定向、超过上限、保存不完整或新出现的未保存内容均阻止清理。保存前检查 Git 属性的文本／换行转换；若会改变待保存字节，在 stash 前拒绝操作。未完成的成果操作会阻止启动新执行，须先恢复该操作。保存后失败可能已把修改放入快照，此时保留工作树和保存引用，重试使用同一操作 ID；不会假装没有发生过保存动作。

独有提交保留任务分支；仅当其他本地分支、远程跟踪引用或标签已包含顶端提交，才比较并删除登记的任务分支。detached HEAD 独有提交建立救援分支。目录已丢失时只移除该目录自身的工作树登记，保留其他缺失工作树，不运行全局 prune。

“清理”保留原任务历史并阻止新执行消息；“删除任务并清理”先保存成果再移除任务记录。旧 `task.delete` 请求未携带 `cleanup` 时继续保留目录与分支。保存成果位于独立 `dualMind.git.artifacts.v1` 记录中，不随任务记录删除。

`git.restore` 从快照的固定提交创建新任务分支与工作树，恢复修改和暂存状态；异常或部分恢复保留新目录，不能覆盖重试期间的人工作业。`task.followup` 创建新的待执行任务，默认从已整合目标或原基点分支开始，可显式选择本地基点。恢复与后续任务均不继承旧验收证据，也不自动开始模型请求。

## 自动上下文摘要

两个角色各自维护请求上下文。默认窗口是 **32,768 Token 估算值**，预留 4,096 输出空间；连接的 `contextWindows[modelId]` 可覆盖真实窗口，允许 8,192–4,194,304。旧连接保存时若未发送该字段，保留已有配置；发送空对象可清除覆盖。窗口配置位于设置的“模型上下文”类别。

估算使用完整请求序列化字节数除以 2，包含角色规则、工具定义及协议包装，并用服务端提供的输入用量提高保守系数。达到可用输入预算 80% 或 512 KiB 请求大小保护的 80% 时整理；目标约为预算的 50%。字节保护与模型 Token 容量是两个不同概念。

摘要使用当前角色的连接／模型，仅提供内部 `submit_context_summary` 工具。保留公开目标、约束、决定、未解决事项和操作引用；角色规则、原需求、当前方案、执行位置与未处理用户消息由宿主提供。优先保留最近四组完整交互，按预算缩减；工具调用与结果不得拆开，Responses 私有推理项不送给摘要模型也不持久化。

旧历史按 UTF-8 码点分块，每次整理最多八次摘要调用，每份摘要不超过 12 KiB。工具结果超过 12,000 字节时模型收到片段和操作 ID，全文仍通过 `read_operation` 分页读取。公开聊天、命令输出与验收记录不随摘要删除。

服务端 HTTP／流错误明确报告上下文超限时，当前角色预算减半并重新整理；同一业务请求最多两轮。无法减少、固定指令超出预算、摘要失败或存储失败时停止推进并保留可恢复记录。摘要不增加工作轮次，也不清零工具、纠错或传输重试预算。模型／工具调用次数只用于诊断，不设累计上限；64 MiB 执行记录上限仍独立生效。

## 三种恢复记录

| 记录         | 保存内容                                     | 用途                                 |
| ------------ | -------------------------------------------- | ------------------------------------ |
| 上下文摘要   | 单个角色公开事实、覆盖的操作位置、哈希与预算 | 减小模型后续请求，重载后恢复事实记忆 |
| 执行恢复日志 | 阶段、方案、证据、逐操作状态和进程身份       | 从原运行继续，避免重放已完成操作     |
| Git 成果快照 | 文件、暂存状态、基点／提交及固定引用         | 清理后或删除任务后恢复到新任务       |

摘要文件先写入并刷盘，再把引用写入执行检查点，最后替换内存历史。恢复时校验运行、角色、哈希与覆盖位置；重建公开上下文，不重放原始私有协议消息。停止、存储失败、旧代次回复及进程未确认规则继续适用。

检查覆盖、运行平台和实际界面验证见[开发日志](./development-log.md)。
